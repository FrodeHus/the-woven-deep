# Haunts Implementation Plan (bones part a: your own fallen heroes)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Echoes and Champions — the fallen-hero encounters that already spawn from Hall standings at their death depth — *become* haunts: they speak their record line when encountered, guard the full equipped gear their hero died with, and can be appeased with an offering instead of fought.

**Architecture:** No new role and no new spawn path. The Hall record grows a `deathInventory` (an instance snapshot of every equipped item at death, captured in `finalizeRun` beside the existing heirloom selection) and the standing carries it plus the record's `cause` (save v15→v16, guest Hall store v3→v4). The existing one-item death reward generalizes into a per-item `createRecordedHeirloom` loop — the whole set for a champion haunt, one loot-stream-picked piece for an echo haunt. Appeasement is a new `offer` command whose need is derived deterministically from the standing plus a content v13 `appeasement` block on the champion template; accepting consumes the item, sets a `neutral` relationship override, fades the haunt through the actor-removal path merchant departure already uses, drops the full inventory, and sets a new `appeased` flag — with no conquest side effects whatsoever. Spoken lines are host-rendered prose from projected record data, exactly like the artifact provenance line.

**Tech Stack:** TypeScript 5.8 ESM, Zod strict schemas, Vitest 3.2, React 19, npm workspaces (`@woven-deep/content`, `@woven-deep/engine`, `@woven-deep/session-core`, `@woven-deep/web`, `@woven-deep/server`).

**Spec:** `docs/superpowers/specs/2026-08-01-haunts-design.md` — read it before starting any task. It is the requirements; this plan is the route. Issue #116 (part a).

## Global Constraints

Every task's requirements implicitly include this section.

- **No new haunt role.** Echoes/Champions *are* the haunts. Placement, spawn depth (exact `deathDepth` match), retention rolls, and encounter/defeat bookkeeping are unchanged — `placeFallenHeroEncounters` and `createFallenHeroRunDecisions` keep their current behavior and their current randomness (one `population-gates` draw per echo candidate, chained after the encounter gates; that ordering is load-bearing).
- **No cross-profile record sharing.** Part b owns the bones pool. Every shape this plan adds (standings as the frozen run input, `deathInventory` on records) is what that pool will sample; nothing here may foreclose it, and nothing here may read another profile's records.
- **No backpack in the death snapshot.** `deathInventory` captures **equipped items only**, exactly the filter `buildSnapshot` already uses.
- **No appeasement-based conquest.** Appeasing never retires a champion, grants no achievement, adds no `newlyConqueredChampionRecordIds` entry, and releases no artifact from the ledger. `defeated` stays `false`; the haunt returns next run. Fighting remains the permanent, greedy option.
- **No engine-side prose.** Spoken lines are host-rendered from projected record data (heroName, role, cause, deathDepth) with killer names resolved from the content pack, following `provenanceLine`'s pattern. The engine emits ids and facts, never sentences.
- **Randomness budget: exactly one new draw in the whole feature** — the echo haunt's single-piece pick at defeat-reward time, on the `loot` stream, taken BEFORE the existing spoils-table roll. The `offer` command's own resolution consumes ZERO randomness (pinned by RNG-stream equality across `resolveOffer`). The champion full-set drop consumes none.
- **Two schema bumps, no more.** Save v15→v16 in Task 1 (freeze `legacyActiveRunV15Schema` FIRST, and — because the shared standing/decision sub-schemas CHANGE SHAPE this time — freeze `legacyFallenStandingPreHaunt` / `legacyFallenDecisionPreHaunt` and wire them into **every** legacy entry version v4–v15; this is the #121 Task-3 lesson in full, with the v13→v14 standings-rewriting migration as the structural template). Content v12→v13 in Task 3, with a migration note in `docs/server-admin/content-configuration.md`. Guest Hall store v3→v4 rides Task 1. Server `record_json` is an opaque envelope — **no DB migration**.
- **Determinism is the product.** Continuous play and split save/reload replay stay byte-identical (`encodeActiveRun` equality) with haunts placed, appeased, and defeated.
- **Demo hashes drift from Task 1 onward** (schemaVersion + standings shape; the run-records demo also has real standings, so its transcript changes with the reward and capture work). Do NOT re-pin mid-plan. Demo/CLI suites are expected-red from Task 1 to Task 10, which re-pins ONCE with per-fixture attribution. Per-task gates run targeted non-demo suites only. **An unexplained delta is a STOP — report BLOCKED, never re-pin over it.**
- **Build gotcha:** demo scripts and CLI tests import `packages/engine/dist`, and workspace-scoped vitest does NOT rebuild it. Before any demo/CLI run: `npm run build --workspace @woven-deep/content && npm run build --workspace @woven-deep/engine`.
- **Wanderer is free by construction.** Wanderer runs produce no records, so they never become haunts; appeasing or defeating a haunt in a Wanderer run writes nothing (the existing finalize gates already guarantee it). Task 9 extends the existing finalize-gate pins rather than adding new gating.

## Spec clarifications recorded here (amend-before-deviating)

Each was an under-specification found while mapping the spec onto the code. Task 11 amends the spec document with all nine.

1. **The spoken line needs a projection, not a fatter event.** `renderEvent(event: PublicEvent)` in `apps/web/src/session/event-log.ts` receives only the event, and `champion.encountered`/`echo.encountered` carry ids alone. Widening those events would drag the frozen legacy *event* schemas into the bump for no gain. Instead `GameplayProjection` gains a `haunts: readonly HauntView[]` block (player-known data: these are the player's own Hall records) and the log renderer takes an optional context built from it. This also hands the client the appeasement need for free, which the spec's "client (UI hint)" requires.
2. **"Light-related cause" is authored, not hardcoded.** No content entry is flagged as a light-related killer, and `cause.killerContentId` is `null` for every death with no killer entity (the dark, the light going out, starvation). The template's `appeasement.causelessCategories` (authored as `[light]`) is applied exactly when `standing.cause === null || standing.cause.killerContentId === null`, which is the spec's universal rule expressed in terms the engine can evaluate.
3. **`validateEchoLootGraph` keeps its authored-content assertion; the relaxation lands at runtime.** The function validates the authored spoils *table* (it must not reach the recorded heirloom content id) — that rule is still correct and still enforced. What relaxes is the runtime duplicate check in `advanceFallenHeroEncounters`: the heirloom may now legitimately appear in an echo's drop, because it arrives via the deathInventory pick rather than the table. That is the spec's "no-heirloom → no-full-set", stated where the code can enforce it.
4. **The offer is an ordinary world action costing `action.drop`.** Every existing balance action cost is authored content; adding an `action.offer` id would be a second content change for no design content. An offering is a giving-away, so it reuses `action.drop`'s cost. The zero-randomness guarantee is pinned on `resolveOffer` itself (RNG-stream equality), not on the surrounding world step, which advances other actors exactly as any action does.
5. **One new `InvalidActionReason`: `'offer.refused'`.** The spec names only the wrong-category refusal. Everything else uses existing reasons — `target.invalid` (no adjacent living retained haunt, or the target is not a haunt), `item.missing` / `item.unavailable` (the offered item is not in the backpack), `run.concluded` (already rejected by the reducer before any of this runs).
6. **The appeased population must be skipped by `advanceFallenHeroEncounters`.** That function throws `fallen hero population ... is incomplete` when a population's actor is missing, and the fade removes the actor. It gains an explicit `continue` for decisions whose `appeased` is `true`. Without it, appeasement crashes the very next world step.
7. **Shipping class tags are `wayfarer`, `lamplighter`, `loomcaller`, `archivist`, `warden`** (`content/classes/*.yaml`, field `classTags`). The spec's illustrative `arcanist` does not exist; the authored map uses the real tags, with `defaultCategories` covering any tag not listed (including future or locked classes).
8. **The killer phrase is a host helper.** `killerPhrase(pack, killerContentId)` returns `` `a ${entry.name.toLowerCase()}` `` for a resolvable monster entry and `'the dark'` for `null` or an id the current pack no longer defines — which is what produces the spec's `"fell to a bone-gnawer at depth 7"` and keeps a content-drifted record readable.
9. **One re-pin, at Task 10, not early.** Determinism-affecting work lands in Tasks 2, 5, 6, and 8 (record capture, champion set drop, echo piece draw, appeasement drops), and the run-records demo carries real standings. Re-pinning before those would mean re-pinning twice and would destroy the attribution discipline. This follows the cursed-items precedent: expected-red demos through the middle of the plan, one attributed re-pin at the end.

export function killerPhrase(pack: CompiledContentPack, killerContentId: OpaqueId | null): string {
  if (killerContentId === null) return 'the dark';

  // A record can outlive the monster that wrote it. "The dark" is the honest degradation: the

export function hauntNeed(
  input: Readonly<{
    standing: FallenHeroStandingSnapshot;
    template: FallenChampionTemplateContentEntry;
  }>,
): readonly ItemCategory[] {
  const { classFavors, causelessCategories, defaultCategories } = input.template.appeasement;
  const favored = input.standing.classTags.flatMap((tag) => classFavors[tag] ?? []);
  // A record with no cause at all, or a death with no killer entity (the dark, the light going
  // out, starvation), wants light -- the spec's one universal rule, authored rather than hardcoded.
  const causeless =
    input.standing.cause === null || input.standing.cause.killerContentId === null
      ? causelessCategories
      : [];
  const union = [...favored, ...causeless];
  // Every haunt must be appeasable: a class whose tags the template does not map falls back to the
  // defaults rather than becoming an unanswerable riddle.
  const resolved = union.length === 0 ? [...defaultCategories] : union;
  return [...new Set(resolved)].sort(compareCodeUnits);
}

/** The living, unappeased haunt the hero is Chebyshev-adjacent to, or `null`. Reads the projection
 * only: the engine re-validates adjacency, need, and ownership, so this is a convenience resolver,
 * never a trust boundary. */
function adjacentHaunt(projection: GameplayProjection): HauntView | null {
  const hero = projection.hero;
  return (
    projection.haunts.find((haunt) => {
      if (haunt.actorId === null || haunt.appeased) return false;
      const actor = projection.actors.find((candidate) => candidate.actorId === haunt.actorId);
      return (
        actor !== undefined &&
        Math.max(Math.abs(Number(actor.x) - Number(hero.x)), Math.abs(Number(actor.y) - Number(hero.y))) === 1
      );
    }) ?? null
  );
}
