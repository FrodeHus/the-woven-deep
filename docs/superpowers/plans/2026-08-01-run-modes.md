# Run Modes (Classic / Wanderer) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** At character creation the player locks the run into **Classic** (today's game, byte-identical: death is final, the Hall remembers) or **Wanderer** (death is a setback — rise again at the top of the current floor, and the Hall never watches).

**Architecture:** The engine stays mode-agnostic in behavior. `mode: 'classic' | 'wanderer'` is data on `ActiveRun` (save v14→v15) that the *hosts* read. Rise-again is a pure host operation: the host stashed `encodeActiveRun(state)` at floor entry (outside `ActiveRun`, in host storage) and `decodeActiveRun`s it back over the concluded run — `finalizeRun` never runs for that death. Accept-death in Wanderer ends the run without calling `finalizeRun` at all. Classic hosts behave exactly as today, regression-pinned.

**Tech Stack:** TypeScript 5.8 ESM, Zod strict schemas, Vitest 3.2, React 19, better-sqlite3, npm workspaces (`@woven-deep/content`, `@woven-deep/engine`, `@woven-deep/session-core`, `@woven-deep/web`, `@woven-deep/server`).

**Spec:** `docs/superpowers/specs/2026-08-01-run-modes-design.md` — read it before starting any task. It is the requirements; this plan is the route. Issue #162.

## Global Constraints

Every task's requirements implicitly include this section.

- **Classic is byte-identical, regression-pinned.** A Classic run must play, save, reload, conclude, and finalize exactly as it does on `main`. The only permitted Classic drift in the whole plan is `schemaVersion: 15` plus the one new `"mode":"classic"` field in the encoded blob — Task 2 re-pins exactly that and nothing else. **An unexplained digest delta is a STOP: report BLOCKED, never re-pin over it.**
- **Wanderer never touches the Hall.** No records, no standings, no champions, no Echoes, no artifact circulation, no heirloom roll (`run-records` stream untouched), no lifetime deltas, no artifact deltas, no unlocks, no achievements — for deaths *and* victories alike. The two finalize call sites (`GuestSession.finalizeConcludedRun`, `ServerPlaySession.maybeFinalize`) are the only gates; `finalizeRun` itself is never modified.
- **The checkpoint lives OUTSIDE `ActiveRun`.** It is host storage (a `sessionStorage` key; a nullable SQL column), never nested in the encoded state. Split save/reload byte-identity is therefore unaffected.
- **No engine-side death-path changes.** `concludeRunOnHeroDeath`, `finalizeRun`, every reducer gate (`reducer.ts:144`'s `run.concluded` rejection), and the save-validation invariants (`save-schema/run-record.ts`: dead hero ⇒ non-null conclusion; living hero ⇒ no `died` conclusion) are untouched.
- **No mid-run mode switching**, no death toll / rise counter / Wanderer penalty beyond lost floor progress, no marked Wanderer Hall records, no unlock gating (both modes open from first launch).
- **Degrade, never crash.** Checkpoint write failure (quota): drop the checkpoint, log the system line `The Deep will not promise a return.`, keep playing — that death then behaves like Classic-without-record. Checkpoint decode failure at rise time: degrade to Accept-death with an apologetic line; never a half-restored state. A death before any checkpoint exists (theoretically impossible — town has no hostiles) degrades to Accept-death.
- **Determinism is the product.** Rise-again is a plain `decodeActiveRun` of a self-consistent blob: every RNG stream rewinds with it, so a re-attempted floor replays byte-identically until the player diverges. That is the accepted, documented pure-rewind decision. `revision`/`turn`/`worldTime` decrease across a rise; the server treats the restore as an authoritative snapshot push so the client's `expectedRevision` re-syncs; the client's command-sequence counter keeps advancing, so no `commandId` collides with the pre-death life.
- **One schema bump, no more.** Save v14→v15 in Task 1: freeze `legacyActiveRunV14Schema` FIRST, then bump `SAVE_SCHEMA_VERSION`, then add exactly ONE ordered migration. Legacy schemas v4–v14 must NOT transitively acquire the new field; every legacy chain arm ends at `migrateV14ToV15`, which defaults `mode: 'classic'`. Content schema is untouched.
- **Build gotcha:** demo scripts and CLI tests import `packages/engine/dist`, and workspace-scoped vitest does NOT rebuild it. Before any demo/CLI run: `npm run build --workspace @woven-deep/content && npm run build --workspace @woven-deep/engine`.
- **CI-only checks, run before pushing:** `npx prettier --write` on every touched file, `npx depcruise` (no import cycles — the `depth-band.ts` extraction is the standing lesson), `npx knip` (no duplicate or unused exports). Keep any new test file well under ~45s so the vitest worker heartbeat stays happy.
- **GitNexus:** run `impact({target, direction: "upstream"})` before modifying any existing symbol and report the blast radius; run `detect_changes()` before every commit.
- **TDD is RED-first** everywhere: write the failing test, run it, watch it fail, then implement. **Commits:** conventional, lowercase, no scope (`feat:`, `fix:`, `test:`, `docs:`, `chore:`).
- Branch: `feat/run-modes`. Do not push until Task 10.

## Spec clarifications recorded here (amend-before-deviating)

Each was an under-specification found while mapping the spec onto the code. Task 10 amends the spec document with all eight.

1. **The server owns the mode; no wire path carries it.** Server-side chargen does not exist (profile runs use `DEFAULT_GUEST_HERO`), and `parseClientMessage` must never trust a client-declared mode. `ServerPlaySession.open()` gains `mode?: RunMode` (default `'classic'`), server-owned exactly like the `canStartClass` guard beside it. Until chargen lands, Wanderer profile runs are reachable only from server-side tests — which is what Task 8 exercises.
2. **Rise/accept ride two new client→server messages, and reuse the existing `state` push.** The spec names the restore push but not the request. Two new `ClientMessage` variants, `rise-again` and `accept-death`, both carrying `commandId`/`expectedRevision` (mandatory for every message in `parseClientMessage`). The reply is the existing `{ type: 'state', snapshot }` — that IS the reconnect-push shape, so no new `ServerMessage` variant and no client-side message-handling branch is needed.
3. **`RunConclusionProjection` carries the mode.** The spec says ConclusionScreen shows the mode but not how it gets there. Adding `mode` to the conclusion projection (player-known data, same as `completionType`) is cleaner than threading a second value through React navigation state, and it is what the guest finalize gate reads back.
4. **Naming: `ServerPlaySession.checkpoint()` is already taken** (the movement dirty-counter, `play-session.ts:420`). The Wanderer checkpoint members are `writeRiseCheckpoint()` / `checkpoint_blob` / `riseAgain()` throughout, so no existing symbol is shadowed or reused for a second meaning.
5. **All six floor-entry paths already land in ONE host branch.** `dispatchIntent` (`packages/session-core/src/dispatch.ts`) returns `kind: 'transition'` for descend-generated, descend-stored, the Final Chamber, ascend, `recallReturn` (the descend branch's anchored arm), and the recall-cast follow-on `recallToTown`. The checkpoint write therefore hooks that single branch in each host, not six call sites.
6. **`GameplayProjection.mode` is required, not optional.** The spec says the projection exposes the mode; a required field makes every consumer's missing-mode bug a `tsc` error rather than a silent `'classic'`.
7. **Non-death Wanderer conclusions gate at the same place.** The spec's §4 death UX covers death only, but §5 says "deaths *and* victories alike". A Wanderer victory (`became-heart`, `broke-cycle`, `refused`) still flows through the host's normal immediate-finalize effect; the gate lives inside `finalizeConcludedRun`/`maybeFinalize`, which clear run state and return an unfinalized, record-null projection.
8. **`legacyActiveRunV14Schema` freezes the top level only.** This bump touches no sub-schema (`item`, `actor`, `floor`, `hero`, standings), so the frozen v14 literal reuses the live sub-schemas for those — the same latitude `legacyActiveRunV11Schema` / `legacyActiveRunV12Schema` already take. The next bump that touches a sub-schema must freeze that sub-schema at that time, as `legacyItemV13` did.

  /**
   * Rewinds a concluded Wanderer run to its floor-entry checkpoint and resumes play. The whole
   * operation is host-side: the engine never sees a "resurrection", it simply receives a fully
   * self-consistent earlier state whose RNG streams, revision, turn, and worldTime all rewind
   * together (the accepted pure-rewind decision -- the floor replays byte-identically until the
   * player diverges). `finalizeRun` is never called for this death, so the Hall, the heirloom
   * roll, the lifetime, and the artifact ledger are all untouched.
   *
   * The command-sequence counter deliberately does NOT rewind: it is session state, not run
   * state, so ids keep climbing and no post-rise command can collide with one the pre-death life
   * already used.
   */
  riseAgain(): boolean {
    if (this.run.mode !== 'wanderer' || this.run.conclusion === null) return false;
    const raw = this.storage.get(CHECKPOINT_KEY);
    if (raw === null) return this.refuseRise();
    let restored: ActiveRun;
    try {
      restored = decodeActiveRun(raw, this.pack);
    } catch (error) {
      if (!(error instanceof SaveLoadError)) throw error;
      return this.refuseRise();
    }
    if (restored.contentHash !== this.pack.hash) return this.refuseRise();
    this.run = restored;
    this.pendingDecision = null;
    this.lastEvents = [];
    this.notice = null;
    this.appendSystemLine('You rise at the floor’s mouth. The Deep did not notice.');
    this.persist();
    this.publish();
    return true;
  }

   * through to Accept-death. Never throws; the concluded run is left exactly as it was. */
  private refuseRise(): boolean {
    this.clearRiseCheckpoint();
    this.appendSystemLine('The Deep offers no way back. This death stands.');
    this.publish();
    return false;

   * Rewinds a concluded Wanderer run to its floor-entry checkpoint. The client's cached
   * `revision` is HIGHER than the restored run's, so the returned `state` message is treated as
   * an authoritative snapshot push (identical in shape to the reconnect push) and the client
   * re-syncs from it -- the client's own command-sequence counter keeps climbing, so no
   * post-rise `commandId` can collide with one the pre-death life already used.
   *
   * `finalizeRun` is never called for this death: no record, no heirloom roll, no lifetime or
   * artifact deltas, no unlocks, no achievements.

  riseAgain(): ApplyOutcome {
    if (this.run.mode !== 'wanderer' || this.run.conclusion === null || this.isFinalized()) {
      return { kind: 'state', snapshot: this.snapshot() };
    }
    const stored = this.repo.get(this.profileId);
    const blob = stored?.checkpointBlob ?? null;
    if (blob === null) return this.acceptDeath();

    try {
      restored = decodeActiveRun(blob, this.pack);
    } catch (error) {
      if (!(error instanceof SaveLoadError)) throw error;
      return this.acceptDeath();
    }
    if (restored.contentHash !== this.pack.hash) return this.acceptDeath();
    this.run = restored;
    this.pendingDecision = null;
    this.lastEvents = [];
    this.checkpointBlob = blob;
    this.persist();
